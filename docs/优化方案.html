01

三个 P0 缺陷

以下全部在本机实测复现，非推测。每一条都会让用户得到与事实相反的结论。

P0-1

控制组只写进报告，verdict() 完全不读它

README 自己写着"若控制组也不通，说明出网受限，'TCP 不通'类结论不可信"。但代码里 control 字段只出现 4 次：赋值 1 次、渲染 2 次、判定函数 0 次。

$ grep -n "control" sitecheck.py 208: def control_check(): 239: R["control"] = control_check() ← 赋值 536: for host, ip, ok in R["control"]: ← 渲染 538: if not any(x[2] for x in R["control"]): ← 渲染 （verdict() 在 307-387 行，一次都没引用）
本机出网受限时，工具照样断言"所有 IP 的 443 端口均不可达 / 可能是服务器下线"，用户会去查服务器，而真正的问题是自己的网络。报告末尾那句警告救不了主结论——用户只看结论行。
P0-2

HTTP 探测失败被当成"服务端拒绝"

http_get() 用 except Exception: pass 吞掉 recv 超时，缓冲区为空，然后 status 被填成 "?"。而 "?" 是 truthy，于是在判定里被归入"有响应但被拒绝"。

# 实测输出：bytes 为 0，一个字节都没收到 140.82.116.4 tcp=True tls=OK match=True http={"status":"?", "bytes":0} layer = HTTP_REJECT verdict = 链路可连通（HTTP ?）—— 网络层没问题，4xx/5xx 多半是反爬 / WAF 策略
HTTP 层完全没响应，工具却告诉用户"网络没问题，是网站反爬"。用户会去翻 WAF 日志，而实际请求根本没发出去。"?"、""、"403" 三种状态被混为一谈。
P0-3

探测方式与用户实际访问方式不一致，且不感知代理

工具全程用裸 socket 直连，而浏览器走系统代理。同一台机器、同一个目标，结果完全相反：

urllib（走系统代理 127.0.0.1:9754） -> 200 裸 socket 直连 140.82.116.4:443 -> TimeoutError curl https://github.com/ -> 200，1.55s # 更矛盾的是：doh_query() 用 urllib，会读 HTTPS_PROXY 走代理 # 于是 UDP DNS 走裸网、DoH 走代理，而 doh_diff 正拿这两个不可比的数据判断"是否污染"
代理环境下工具必然报"不通"，而浏览器一切正常。README 里那句"结论和用户实际体验冲突时，先怀疑工具"说明作者已意识到问题，但代码没解决。
P0-4

证书 SAN 通配符匹配有安全漏洞，可跨域命中

sitecheck.py:129 的 host.endswith(x[2:]) 丢掉了点，退化成纯后缀匹配：

host 证书 SAN 应判 实际 evilexample.com *.example.com 否 是 ← BUG a.b.example.com *.example.com 否 是 ← BUG notexample.com *.example.com 否 是 ← BUG
整个工具的"真实 IP"结论完全建立在这个函数上。一旦 DNS 被污染到持有 *.example.com 通配证书的 CDN 节点（Cloudflare 免费证书默认就是这种形态），工具会把伪造 IP 认证成真实 IP，并建议写进 hosts——恰好是它最想避免的事。
02

判定引擎：从 if-else 瀑布到状态机

现状是 81 行 if-else，优先级隐含在代码顺序里，且有盲区。目标是把判定变成纯函数，输入 dataclass，可完全脱离网络做单测。

03

性能：53 秒 → 8 秒以内

三层全串行。单个死 IP 就吃掉 8 秒超时，6 个候选（4 个不通）实测 53 秒。而 dns_bench.py 里已经在用线程池了——主流程反而没用，属于疏漏。

候选 IP（N 个）串行，N×24s~3s两阶段：先并发 TCP 筛活，再并发 TLS+HTTP

落地路线图

阶段 1 的六项改动合计约 200 行，但能让工具从"看起来专业"变成"结论可信"。

阶段 1 · 止血1~2 天
目标：不再输出错误结论
  • 修复 SAN 匹配（含回归测试）
  • 控制组接入判定第 0 步
  • 拆分 NO_RESPONSE / MALFORMED，新增判定分支
  • 探测并发化（53s → < 8s）
  • --ip 格式校验、提权命令用 list2cmdline
  • 修掉两处硬编码绝对路径；dist 出库，补 LICENSE
阶段 2 · 可信3~5 天
目标：结论与用户实际体验一致
  • 代理探测（env → WinINET → PAC），HTTP 双路径对照
  • DoH 强制 ProxyHandler({})，与 UDP DNS 语义对齐
  • http_probe 重写：只读 header、4 种状态、TTFB
  • 证书链降级重试（自签站点也能判真身）
  • AAAA 记录支持
  • verdict.py 抽成纯函数，结论带 evidence
阶段 3 · 工程化3~5 天
目标：别人能参与，改动不会退化
  • 拆包 src/sitecheck/* + pyproject.toml
  • pytest 覆盖判定树全部分支（fixture，不打网络）
  • GitHub Actions：ruff + pytest + 三平台构建 + tag 发版
  • dns-bench / hosts-audit 合并为子命令
  • 备份目录迁移 + --restore
阶段 4 · 增强按需
目标：提升产品价值
  • 批量检测 + 表格视图（可排序筛选）
  • 导出 JSON / HTML
  • TLS 深度检查（有效期 / 链完整性 / HSTS / OCSP）
  • 诊断建议引擎（输出可执行命令清单）

这个项目的判断力在同类工具里属于上乘：用证书而非 DNS 判定真身、区分 DNS 层与 SNI 层的封锁、克制地建议改 hosts、把控制组写进报告。这些不是查文档能得到的，是踩过坑才有的。

问题在于这些判断只停留在文档和注释里，没有落到代码结构上——控制组的警告写在 README 却没写进 verdict()；"先怀疑工具"的告诫写在 README 却没实现代理感知；证书判定是最核心的价值，匹配函数却有个可跨域命中的 bug。

所以第一优先级不是加功能，而是把已经想清楚的事真正实现。
