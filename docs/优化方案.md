# sitecheck 优化方案

> **一句话结论**：这个项目的判定哲学是对的 —— 用证书 SAN 判定 IP 真身、只在 hosts 真能解决问题时才建议改、把控制组写进报告。但实现跟不上设计：**三个 P0 缺陷会让工具给出与事实相反的结论**，且单次检测耗时 53 秒。优化重点不是加功能，而是把"结论可信"这件事真正做到。

审查对象：`45944831/sitecheck` @ `1dde086`（v1.0，2026-10-03）
审查方式：源码逐行审查 + 本机实测复现（Python 3.13 / Windows）
文档日期：2026-10-29

**做得好的地方（必须保留）**

1. **用证书 SAN 判定 IP 真身**，而不是相信 DNS。这是整个工具最有价值的判断，也是它区别于普通 ping 工具的地方。
2. **hosts 建议的克制**。区分了 `DNS 层` 和 `SNI 层`，明确指出"SNI 被拦时改 hosts 无效"。绝大多数同类工具会无脑建议改 hosts。
3. **控制组设计**。意识到"探测环境本身可能不可信"，这是元认知层面的正确设计。
4. **把 hosts 里已有的条目纳入候选 IP**。理解用户真实问题是"我这条 hosts 还能用吗"，而不是"DNS 说什么"。
5. **`build.py` 用 Python 驱动而非 bat**，绕开了 `chcp 65001` 截断命令行的问题 —— 这个细节说明作者踩过坑且做了记录。

这些设计判断的质量高于代码质量。优化的方向应该是**让实现追上设计**，而不是推倒重来。

## 2. 实测：三个会误导用户的 P0 缺陷

以下全部在本机复现，非推测。

### P0-1　控制组只写进报告，不参与判定

`README.md` 自己写着：

> 若控制组也不通，说明当前网络出网受限，报告中"TCP 不通"类结论不可信。

但代码里 `control` 字段只出现 4 次：赋值 1 次、渲染 2 次、`verdict()` 里 **0 次**。

```bash
$ grep -n "control" sitecheck.py
208:def control_check():
225:  ... "control": [], ...
239:  R["control"] = control_check()
536:  for host, ip, ok in R["control"]:      # render
538:  if not any(x[2] for x in R["control"]): # render
```

**后果**：本机出网受限时，工具照样输出"所有候选 IP 的 443 端口均不可达 / 可能是服务器下线"，用户会去查服务器，而真正的问题是自己的网络。报告末尾那句警告救不了主结论 —— 用户只看结论行。

实测中确实出现了这个矛盾：同一次运行里 `control` 报告 github.com 通，而 `probes` 里同一 IP `tcp=False`，`verdict` 仍然断言 TCP 不通。

### P0-2　HTTP 探测失败被当成"服务端拒绝"

`http_get()` 用 `except Exception: pass` 吞掉 `recv` 超时，缓冲区为空，然后：

```python
st = re.match(r"HTTP/[\d.]+ (\d+)", txt)
return {"status": st.group(1) if st else "?", ...}
```

`"?"` 是 truthy，于是在 `verdict()` 里：

```python
responded = [p for p in genuine if p["http"] and p["http"]["status"]]  # "?" 通过
rejected  = [p for p in responded if not p["http"]["status"].startswith(("2","3"))]  # 归入
```

实测输出（`bytes: 0`，一个字节都没收到）：

```
140.82.116.4  tcp=True tls=OK match=True  http={"status":"?", "bytes":0}
layer   = HTTP_REJECT
verdict = 链路可连通（HTTP ?）—— 网络层没问题，4xx/5xx 多半是服务端的反爬 / 地域 / WAF 策略
```

**后果**：HTTP 层完全没响应，工具却告诉用户"网络层没问题，是网站反爬"。用户会去翻 WAF 日志，而实际上请求根本没发出去。`"?"`（非标准响应）、`""`（无响应）、`"403"`（真拒绝）三种状态被混为一谈。

### P0-3　探测方式与用户实际访问方式不一致，且不感知代理

同一台机器、同一个目标，两种方式结果完全相反：

```
urllib（走系统代理 127.0.0.1:9754）  ->  200
裸 socket 直连 140.82.116.4:443      ->  TimeoutError
curl https://github.com/             ->  200，1.55s
```

工具全程使用**裸 socket 直连**（`tcp_ping` / `tls_handshake` / `http_get` 都是 `socket.create_connection`），而用户的浏览器走系统代理 / PAC。在必须经代理出网的环境里，工具必然报"不通"，而浏览器一切正常。

更矛盾的是 `doh_query()` 用的是 `urllib.request.urlopen` —— **它会读 `HTTPS_PROXY` 环境变量走代理**。于是同一个工具里，UDP DNS 走裸网、DoH 走代理，两者结果不可比，而 `doh_diff` 正是拿这两个不可比的数据去判断"是否污染"。

`README.md` 里那句"结论和用户实际体验冲突时，先怀疑工具"说明作者已经意识到这个问题，但代码里没有解决。

### P0-4　证书 SAN 通配符匹配有安全漏洞

`sitecheck.py:129`：

```python
out["match"] = any(host == x or (x.startswith("*.") and host.endswith(x[2:])) for x in san)
```

`x[2:]` 丢掉了点，`endswith` 变成后缀匹配：

| host | 证书 SAN | 应判 | 实际 | |
|---|---|---|---|---|
| `evilexample.com` | `*.example.com` | 否 | **是** | BUG |
| `a.b.example.com` | `*.example.com` | 否（RFC 6125 通配只匹配一级） | **是** | BUG |
| `notexample.com` | `*.example.com` | 否 | **是** | BUG |

**后果**：整个工具的"真实 IP"结论完全建立在这个函数上。一旦 DNS 被污染到一个持有 `*.example.com` 通配证书的 CDN 节点（Cloudflare 免费证书默认就是 `*.domain` 形态），工具会把伪造 IP 认证成"真实 IP"，并建议用户写进 hosts。这恰好是工具最想避免的事。

`gf_probe.py:25` 有同样的代码，同样的 bug。

## 4. 优化方案

### 4.1 判定引擎：从 if-else 瀑布到证据链状态机

**现状问题**：`verdict()` 是一串 81 行的 if-else，判定优先级隐含在代码顺序里，且存在盲区（HTTP 无响应 → 落到"未知"）。控制组、代理状态这些全局证据完全不参与判定。

**目标设计**：三层结构。

```
第 1 层  ProbeResult      单个 IP 的结构化探测结果（每层一个状态枚举）
第 2 层  IpVerdict        单个 IP 的结论（可达？证书匹配？HTTP 可用？）
第 3 层  OverallVerdict   聚合全部 IP + 全局证据（控制组、代理、DNS 一致性）→ 最终结论
```

**状态枚举**（替代现在的字符串前缀判断）

```python
class Dns(str, Enum):
    OK = "ok"; NXDOMAIN = "nxdomain"; EMPTY = "empty"; TIMEOUT = "timeout"

class Tcp(str, Enum):
    OK = "ok"; REFUSED = "refused"; TIMEOUT = "timeout"; RESET = "reset"

class Tls(str, Enum):
    OK = "ok"; CERT_MISMATCH = "cert_mismatch"; CHAIN_UNTRUSTED = "chain_untrusted"
    BLOCKED = "blocked"          # TCP 通但握手无响应 / RST —— SNI 层特征

class Http(str, Enum):
    OK = "ok"                    # 2xx/3xx
    REJECT = "reject"            # 4xx/5xx，且拿到了合法状态行
    NO_RESPONSE = "no_response"  # 一个字节都没收到  ← 新增，当前缺失
    MALFORMED = "malformed"      # 收到数据但不是 HTTP  ← 新增，当前混进 "?"
```

**判定树**（优先级显式化，每步有证据）

```python
def overall_verdict(probes, dns, control, proxy) -> Verdict:
    # 0. 环境可信度优先 —— 这是最重要的改动
    if control and not any(c.ok for c in control):
        return Verdict(INCONCLUSIVE, "本机出网受限，本次探测结果不可信",
                       evidence="控制组全部不通")

    genuine = [p for p in probes if p.tls is Tls.OK and p.cert_match]
    served  = [p for p in genuine if p.http in (Http.OK, Http.REJECT)]

    # 1. 有 IP 能完成完整访问
    if any(p.http is Http.OK for p in genuine):
        return Verdict(SUCCESS, ...)
    # 2. 有 IP 链路通但被服务端拒绝
    if any(p.http is Http.REJECT for p in genuine):
        return Verdict(HTTP_REJECT, ...)
    # 3. 有 IP TLS 通、证书匹配，但 HTTP 无响应  ← 当前落到"未知"的场景
    if genuine:
        return Verdict(HTTP_NO_RESPONSE,
                       "TLS 与证书均正常，但 HTTP 层无响应",
                       evidence="建议检查代理设置 / 该 IP 是否只提供非 HTTP 服务")
    # 4. TCP 通、TLS 通、证书不匹配 → 污染
    if any(p.tls is Tls.OK and not p.cert_match for p in probes):
        return Verdict(DNS_POISONED, ...)
    # 5. TCP 通、TLS 被切断 → SNI
    if any(p.tcp is Tcp.OK and p.tls is Tls.BLOCKED for p in probes):
        return Verdict(TLS_BLOCKED, "改 hosts 无效", ...)
    # 6. 全部 TCP 不通
    if probes and all(p.tcp is not Tcp.OK for p in probes):
        return Verdict(TCP_BLOCKED, ...)
    # 7. DNS 无记录
    if not any(d.ips for d in dns):
        return Verdict(DNS_FAIL, ...)
    return Verdict(UNKNOWN, ...)
```

**关键收益**

- 控制组从"报告末尾的警告"升级为"判定第 0 步的否决权"，README 的承诺真正落地。
- `HTTP_NO_RESPONSE` 成为独立结论，不再被误报为反爬，也不再落入"未知"。
- 判定逻辑纯函数化，输入是 dataclass，可以完全脱离网络做单元测试 —— 这是当前最缺的东西。

**每条结论必须带 `evidence` 字段**，渲染时展示"为什么这么判"。这是可信工具和黑盒工具的分界线。

### 4.2 探测层：并发 + 代理感知 + HTTP 重写

#### (a) 并发化 —— 53 秒降到 6 秒以内

现状是三层全串行：6 个 DNS → 2 个 DoH → 2 个控制组 → N 个候选 IP（每个 TCP + TLS + HTTP）。

```python
# 现状：analyze() 279-290
for i, ip in enumerate(cands, 1):
    tcp_ok, tcp_ms = tcp_ping(ip)          # 最坏 8s
    if tcp_ok:
        info["tls"] = tls_handshake(ip, domain)   # 最坏 8s
        if ...: info["http"] = http_get(ip, domain)  # 最坏 8s
```

单个死 IP 就吃掉 8 秒。实测 6 个候选（4 个不通）耗时 53 秒。

```python
# 目标：分阶段并发
with ThreadPoolExecutor(max_workers=6) as ex:
    dns_res = list(ex.map(lambda s: udp_query(domain, s[0]), UDP_RESOLVERS))
    doh_res = list(ex.map(lambda e: doh_query(e, domain), DOH_ENDPOINTS))
    ctl_res = list(ex.map(control_probe, CONTROLS))

# 两阶段：先并发 TCP 筛掉死的，再并发 TLS+HTTP
alive = [ip for ip, ok in zip(cands, ex.map(tcp_ping, cands)) if ok]
with ThreadPoolExecutor(max_workers=8) as ex:
    probes = list(ex.map(lambda ip: full_probe(ip, domain), alive))
```

预期：DNS 阶段 ~1s（6 个并发），探测阶段 ~2-3s（8 并发 × 最坏 8s / 8），总计 **3~5 秒**。给 GUI 一个确定进度条（总步数可数）。

`dns_bench.py` 已经在用 `ThreadPoolExecutor(max_workers=12)`，说明作者会写并发 —— 主流程反而没用，属于疏漏而非能力问题。

#### (b) 代理感知 —— 解决"结论与体验冲突"

这是 P0-3 的正解。不是"支持代理"，而是**同时报告两条路径**。

```python
def detect_proxy() -> ProxyInfo | None:
    """按 Windows 实际生效顺序探测：环境变量 → WinINET 注册表 → PAC"""
    for k in ("https_proxy", "HTTPS_PROXY", "http_proxy", "HTTP_PROXY"):
        if v := os.environ.get(k):
            return ProxyInfo(kind="env", url=v, source=k)
    try:  # 注册表：IE/系统代理设置
        import winreg
        with winreg.OpenKey(winreg.HKEY_CURRENT_USER,
                r"Software\Microsoft\Windows\CurrentVersion\Internet Settings") as key:
            if winreg.QueryValueEx(key, "ProxyEnable")[0]:
                return ProxyInfo(kind="wininet",
                                 url=winreg.QueryValueEx(key, "ProxyServer")[0],
                                 source="WinINET")
    except OSError:
        pass
    return None
```

探测策略：

| 层 | 直连 | 经代理 | 说明 |
|---|---|---|---|
| UDP DNS (53) | ✓ | — | DNS 本来就不走 HTTP 代理，保持裸网 |
| DoH | ✓ **强制 `ProxyHandler({})`** | — | 与 UDP DNS 语义一致，否则 `doh_diff` 无意义 |
| TCP/TLS | ✓ | — | 代理下 TCP 探测意义有限，但保留 |
| HTTP | ✓ | ✓ **代理存在时必做** | 两列并列展示 |

结论里必须显式标注：

```
结论：可以直连（经代理，HTTP 200）
      直连不通 —— 本机配置了代理 127.0.0.1:9754，浏览器走代理，因此"直连不通"不影响你的实际访问。
```

这一条就能消灭"工具说打不开，但浏览器明明能打开"这类最常见的困惑。

#### (c) HTTP 探测重写

现状三个问题：读满 300 KB、异常吞掉、状态混淆。

```python
def http_probe(ip, host, path="/", timeout=8.0, proxy=None) -> HttpResult:
    """只读到 header 结束 + 少量 body（取 title），区分 4 种状态"""
    raw = b""
    try:
        sock = connect(ip, host, proxy)          # 直连或 CONNECT 隧道
        sock.sendall(request_bytes(host, path))
        t0 = time.perf_counter()
        while b"\r\n\r\n" not in raw:            # 只等 header
            chunk = sock.recv(8192)
            if not chunk:
                break
            raw += chunk
            if len(raw) > 64 * 1024:             # 防御超大 header
                break
        ttfb = (time.perf_counter() - t0) * 1000
        if not raw:
            return HttpResult(Http.NO_RESPONSE, ttfb=ttfb)      # 明确：一个字节都没收到
        head, _, body = raw.partition(b"\r\n\r\n")
        m = re.match(rb"HTTP/[\d.]+ (\d{3})", head)
        if not m:
            return HttpResult(Http.MALFORMED, ttfb=ttfb, raw=head[:200])
        status = int(m.group(1))
        # title 需要少量 body
        if b"<title" in body.lower() or not body:
            body += read_some(sock, 8192)
        ...
        return HttpResult(Http.OK if status < 400 else Http.REJECT,
                          status=status, ttfb=ttfb, ...)
    except socket.timeout:
        return HttpResult(Http.NO_RESPONSE if not raw else Http.MALFORMED, ...)
```

同时**统一 ALPN**：`tls_handshake` 和 `http_probe` 用同一个 `SSLContext`。若协商到 h2，就不要再发 HTTP/1.1 明文请求（会得到 `MALFORMED`），要么用 `h2` 库发帧，要么在 HTTP 探测时只声明 `http/1.1` 并在报告里说明"HTTP/2 已由 ALPN 确认，本次请求走 HTTP/1.1"。

#### (d) 证书链不可信时降级

```python
def tls_probe(ip, host, timeout=8.0) -> TlsResult:
    # 第一轮：严格校验（同时拿到 SAN 和链状态）
    try:
        return _handshake(ip, host, verify=ssl.CERT_REQUIRED)
    except ssl.SSLCertVerificationError as e:
        # 第二轮：只取证书内容判 SAN，链状态单独标记
        r = _handshake(ip, host, verify=ssl.CERT_NONE)
        r.chain_trusted = False
        r.chain_error = str(e)[:80]
        return r
```

自签/私有 CA 站点因此也能判定真身，只是标注"证书链不受信任"。现在这类站点会直接 `ok=False`，被当成"无法确认"。

### 4.3 安全修复

#### (a) SAN 匹配（P0-4）

```python
def cert_matches(host: str, san: Iterable[str]) -> bool:
    """RFC 6125：通配符只匹配最左一级标签，且不跨域"""
    host = host.lower().rstrip(".")
    for raw in san:
        name = raw.lower().rstrip(".")
        if name.startswith("*."):
            suffix = name[2:]                      # "example.com"
            if "." not in host:
                continue
            label, _, rest = host.partition(".")
            if rest == suffix and label:            # 必须有点分隔 + 只剩一级
                return True
        elif host == name:
            return True
    return False
```

回归用例（应写进 `tests/test_cert.py`）：

#### (c) hosts 编码与原子写入

现状 `utf-8-sig` 读、`utf-8` 写，原文件里的 GBK 注释会被 `errors="replace"` 换成 `\ufffd` 再写回，**不可逆损坏**。

```python
def read_hosts_text(path) -> tuple[str, str]:
    raw = Path(path).read_bytes()
    for enc in ("utf-8-sig", "utf-8", "gbk", "latin-1"):   # 逐级降级
        try:
            return raw.decode(enc), enc
        except UnicodeDecodeError:
            continue
    return raw.decode("latin-1"), "latin-1"

def write_hosts_atomic(path, text, encoding):
    tmp = Path(path).with_suffix(".sitecheck.tmp")
    tmp.write_text(text, encoding=encoding, newline="")     # 原编码写回
    os.replace(tmp, path)                                    # 原子替换
```

## 8. 总结

这个项目的**判断力**在同类工具里属于上乘：用证书而非 DNS 判定真身、区分 DNS 层与 SNI 层的封锁、克制地建议改 hosts、把控制组写进报告。这些判断不是查文档能得到的，是踩过坑才有的。

问题在于这些判断**只停留在文档和注释里，没有落到代码结构上**：

- 控制组的警告写在 README，没写进 `verdict()`
- "先怀疑工具"的告诫写在 README，代理感知没实现
- 证书判定是最核心的价值，匹配函数却有个可跨域命中的 bug

所以优化的第一优先级不是加功能，而是**把已经想清楚的事真正实现**。阶段 1 的六项改动量都不大（合计约 200 行），但能让工具从"看起来专业"变成"结论可信"。

之后再用阶段 2 解决"结论与体验一致"，阶段 3 解决"别人能接手"。做完这三步，这个工具就有了长期维护的基础。
